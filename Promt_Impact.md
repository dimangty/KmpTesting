# Prompt For OpenCode Desktop Impact Analysis

Проверено через `/Applications/OpenCode.app/Contents/MacOS/opencode-cli`:
- для одноразового запуска используется `opencode run`
- diff-файл прикладывается через `-f/--file`
- после `-f "$DIFF_FILE"` обязательно ставь `--`, иначе `opencode-cli` может принять сам prompt за ещё один путь к файлу
- для `opencode-cli` лучше явно написать в prompt: `Открой и прочитай файл ...`, потому что одного attachment локальной модели часто недостаточно
- для CLI указывай относительный путь `./DIFF_FILE`, а не `/DIFF_FILE`
- для desktop не проси модель открыть локальный путь: используй уже приложенное вложение `@DIFF_FILE`
- для `qwen3-coder:30b` формат держится лучше, если жёстко запретить вводный абзац и не давать модели выдумывать ручное локальное тестирование
- в `Протестировано локально` безопаснее разрешать только то, что реально видно в diff: добавленные/изменённые тесты; иначе `N/A`

Для повторного использования просто замени `DIFF_FILE` на имя нужного diff-файла.

Для локальной модели удобнее начинать с:
1. `review_master_app_only.diff` - короче и хорошо показывает, что prompt умеет игнорировать meta-шум.
2. `review_kitchentips_feature.diff` - полный feature diff с Android/iOS/shared/test coverage.
3. `review_master.diff` - самый шумный вариант, если хочешь проверить устойчивость к `.idea`, skills и архивам.

**Prompt для opencode-desktop**

```text
Делай impact analysis только по вложению `@DIFF_FILE`.

Файл уже приложен к сообщению.
Не проси прислать его повторно.
Не пытайся открыть локальный путь вроде `./DIFF_FILE` или `/DIFF_FILE`.
Используй только содержимое вложения `@DIFF_FILE`.

Это не code review и не пересказ diff по файлам.
Нужно подготовить именно impact analysis по изменениям.

Отвечай строго только на русском языке.
Ничего не пиши до строки `# Impact analysis`.
Если начал ответ с вводного абзаца, summary, пересказа diff или фразы вроде `В этом diff`, `Изменения включают`, `This diff`, `Ниже анализ`, такой ответ невалиден и должен быть полностью переписан.

Правила:
- Анализируй только продуктовые изменения под `shared/`, `androidApp/`, `iosApp/`.
- Игнорируй meta/tooling-шум: `.idea/`, `xcuserdata/`, архивы, skill-файлы, tooling, `gradle/config.properties` и другие непродуктовые изменения.
- Группируй изменения по смыслу и пользовательскому эффекту, а не по файлам.
- Если одна и та же фича затронула shared, Android, iOS, navigation и DI, опиши это одним сквозным пунктом, а не пятью отдельными.
- Каждый пункт в разделе `Impact analysis` должен иметь формат `- Краткое название #00F|#0F0|#F00: ...`.
- `#00F` используй для небольших текстовых, контентных или косметических изменений.
- `#0F0` используй для изменений логики, навигации, экрана, состояния, DI или тестов без полного переписывания модуля.
- `#F00` используй только для крупных и действительно тяжёлых изменений уровня модуля, основного роутинга или архитектуры.
- Не перечисляй импорты, имена функций и строки кода без необходимости. Нужна суть изменения, а не листинг diff.
- Не хвали реализацию и не ищи баги: это не ревью.
- Не придумывай скрытые требования, ручные проверки, сборки, прогон на устройстве или подтверждения, которых нет в diff.
- Если в diff добавлены или изменены тесты, можешь использовать это как подтверждённое покрытие и перечислить в `Протестировано локально`.
- Если в diff изменено несколько тестовых файлов, перечисли их в `Протестировано локально` отдельными пунктами и коротко укажи, что именно они покрывают.
- Если подтверждённых тестов в diff нет, в разделе `Протестировано локально` пиши только `N/A`.
- В разделе `Сверено с Figma` всегда пиши `N/A`.
- В разделе `Рекомендации к тестированию` перечисляй только конкретные сценарии, платформы, экраны и точки входа, на которые реально влияют изменения.
- Не добавляй шаблонные рекомендации вроде `проверить интернет`, `проверить разные устройства`, `проверить ориентацию`, `проверить permissions`, если diff явно этого не затрагивает.
- Каждая строка в `Рекомендации к тестированию` должна прямо вытекать из одного из пунктов `Impact analysis`.
- Если diff выглядит как частичный срез большого изменения, не выдумывай недостающие части. Описывай только то, что видно в приложенном diff.
- Не дублируй одну и ту же мысль в `Impact analysis` и `Рекомендации к тестированию`.
- Если весь diff про одну фичу, обычно достаточно 2-5 пунктов в `Impact analysis`.
- Обычный английский текст запрещён. Английский допустим только внутри путей, имён файлов, идентификаторов и literal-строк из diff.
- Перед отправкой проверь, что все 4 раздела присутствуют и ни один из них не пустой.

Формат ответа:
# Impact analysis
- ...
- ...

## Сверено с Figma
N/A

## Протестировано локально
- ...
или
N/A

## Рекомендации к тестированию
- ...
- ...
```
