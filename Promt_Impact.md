# Prompt For OpenCode Desktop Impact Analysis

Обновлено с учетом нового скилла `t-impact-analysis` из `/Users/dmitry/Downloads/SKILL (1).md`.

Что изменено в этой версии:
- формат ответа теперь ближе к готовому комментарию в трекер, а не к короткому internal summary
- severity теперь в формате `🔴 High` / `🟢 Mid` / `🔵 Low`
- добавлены обязательные разделы `Зависимые задачи` и `Требуемые настройки / доступы`
- текст должен быть менеджерским: без перечисления файлов, классов, методов и библиотек в обычном описании
- prompt по-прежнему адаптирован под твой сценарий с приложенным `diff`-файлом, а не под live `git diff origin/develop...HEAD`

Проверено через `/Applications/OpenCode.app/Contents/MacOS/opencode-cli`:
- для одноразового запуска используется `opencode run`
- diff-файл прикладывается через `-f/--file`
- после `-f "$DIFF_FILE"` обязательно ставь `--`, иначе `opencode-cli` может принять сам prompt за еще один путь к файлу
- для `opencode-cli` лучше явно написать в prompt: `Открой и прочитай файл ...`, потому что одного attachment локальной модели часто недостаточно
- для CLI указывай относительный путь `./DIFF_FILE`, а не `/DIFF_FILE`
- для desktop не проси модель открыть локальный путь: используй уже приложенное вложение `@DIFF_FILE`
- для `qwen3-coder:30b` формат держится лучше, если жестко запретить вводный абзац, пересказ diff по файлам и выдуманное ручное тестирование

Для повторного использования просто замени `DIFF_FILE` на имя нужного diff-файла.

Для локальной модели удобнее начинать с:
1. `review_master_app_only.diff` - короче и хорошо показывает, что prompt умеет игнорировать meta-шум.
2. `review_kitchentips_feature.diff` - полный feature diff с Android/iOS/shared/test coverage.
3. `review_master.diff` - самый шумный вариант, если хочешь проверить устойчивость к `.idea`, skills и архивам.

**Prompt для opencode-desktop**

```text
Сделай Impact Analysis только по вложению `@DIFF_FILE`.

Файл уже приложен к сообщению.
Не проси прислать его повторно.
Не пытайся открыть локальный путь вроде `./DIFF_FILE` или `/DIFF_FILE`.
Используй только содержимое вложения `@DIFF_FILE`.

Это не code review и не пересказ diff по файлам.
Нужно подготовить готовый markdown-комментарий для трекера в стиле Impact Analysis.

Отвечай строго только на русском языке.
Ничего не пиши до строки `## Impact Analysis`.
Если начал ответ с вводного абзаца, summary, пересказа diff или фразы вроде `В этом diff`, `Изменения включают`, `This diff`, `Ниже анализ`, такой ответ невалиден и должен быть полностью переписан.

Правила анализа:
- Анализируй только продуктовые изменения под `shared/`, `androidApp/`, `iosApp/`.
- Игнорируй meta/tooling-шум: `.idea/`, `xcuserdata/`, архивы, skill-файлы, tooling, `gradle/config.properties` и другие непродуктовые изменения.
- Сначала сгруппируй изменения по смысловым блокам и пользовательскому эффекту, а не по файлам.
- Если одна и та же фича затронула shared, Android, iOS, navigation и DI, опиши это как один сквозной блок, а не как набор файлов.
- Пиши так, как будто текст читает менеджер или QA без кода перед глазами.
- В обычном тексте не перечисляй пути, имена файлов, классов, методов, библиотек и внутренние технические детали без крайней необходимости.
- Не описывай строки кода, импорты и рефакторинг ради рефакторинга.
- Не хвали реализацию и не ищи баги: это не ревью.
- Не придумывай скрытые требования, ручные проверки, сборки, прогон на устройстве или подтверждения, которых нет в diff.
- Если diff выглядит слишком частичным и для корректного Impact Analysis реально не хватает контекста, кратко напиши об этом только в секции `### Зависимые задачи` или `### Требуемые настройки / доступы`, не ломая общий формат ответа.

Правила severity:
- Используй только три варианта:
  - `🔴 High`
  - `🟢 Mid`
  - `🔵 Low`
- Новый модуль, новый экранный флоу, новый маршрут, изменение API-контракта, DI-цепочки, схемы данных или сквозной feature flow обычно помечай как `🔴 High`.
- Изменение логики без полного переписывания большого модуля, новые утилиты, логирование, дополнительный пользовательский сценарий - это обычно `🟢 Mid`.
- Тексты, стили, косметика, переводы, константы без заметного влияния на логику - это обычно `🔵 Low`.
- Каждая строка в секции `### Изменения` должна начинаться строго с одной из меток: `🔴 High -`, `🟢 Mid -`, `🔵 Low -`.

Правила по разделам:
- `### Описание изменений`: 1-3 предложения о сути задачи без технического листинга.
- `### Изменения`: список значимых изменений с severity-маркировкой.
- `### Зависимые задачи`: если по diff зависимости не видны, пиши `N/A`.
- `### Требуемые настройки / доступы`: указывай только то, что реально видно из diff; если ничего такого нет, пиши `N/A`.
- `## Сверено с Figma`: если diff не дает прямого подтверждения, пиши `N/A`.
- `## Протестировано локально`: разрешено указывать только то, что можно обоснованно вывести из diff:
  - добавленные или измененные автотесты;
  - если подтвержденных тестов в diff нет, пиши `N/A`.
- Если в diff изменено несколько тестовых файлов, перечисли их как отдельные пункты, но описывай по смыслу, а не путями.
- `## Рекомендации к тестированию`: перечисляй только конкретные пользовательские сценарии, платформы, экраны и точки входа, которые реально следуют из diff.
- Не добавляй шаблонные рекомендации вроде `проверить интернет`, `проверить разные устройства`, `проверить ориентацию`, `проверить permissions`, если diff явно этого не затрагивает.
- Каждая строка в `## Рекомендации к тестированию` должна прямо вытекать из одного из пунктов `### Изменения`.
- Если секция не применима, пиши `N/A`, а не пустой заголовок.

Ограничения на стиль:
- Не пиши обычный английский текст. Английский допустим только внутри терминов severity `High/Mid/Low`, общеупотребимых названий фич из diff и literal-значений.
- Не придумывай новую предметную терминологию поверх diff. Если в diff речь про советы, чек-лист, экран профиля и навигацию, описывай именно это, без странных синонимов и лишних сущностей.
- Не дублируй одну и ту же мысль в `### Описание изменений`, `### Изменения` и `## Рекомендации к тестированию`.
- Не делай ответ слишком раздутым: для одной фичи обычно достаточно 2-5 пунктов в `### Изменения`.
- Перед отправкой проверь, что все секции из шаблона ниже присутствуют и ни одна не пустая.

Формат ответа:
## Impact Analysis

### Описание изменений
...

### Изменения
🔴 High - ...
или
🟢 Mid - ...
или
🔵 Low - ...

### Зависимые задачи
N/A
или
...

### Требуемые настройки / доступы
N/A
или
...

---

## Сверено с Figma
N/A
или
...

---

## Протестировано локально
N/A
или
- ...

---

## Рекомендации к тестированию
N/A
или
- ...
```
